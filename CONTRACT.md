# deadgate contract

This contract is the executable spec for deadgate. Every obligation below maps to at least one test in the test suite, and the mapping is named under each obligation.

## The boundary

Deadgate asks whether it ran. Finaltree asks what it ran on, and blindgate asks what it read. Deadgate reconciles the required status checks in branch protection, the jobs CI actually executes, and the trigger conditions inside each workflow, and it names the required checks that exist only on paper.

## Slice 2 preamble

The seed concept stands as slice 1. Slice 2 is the reconciliation slice, and its readings were established by probing synthetic inputs written in the real forms of the three sources, with the probe programs kept in the builder scratch and their findings stated here so the obligations rest on evidence rather than on habit.

The protection probe used a payload in the form the GitHub branch protection API returns for one branch. The load bearing part stands under a required_status_checks object holding a checks list whose entries each carry a context field and an app_id field, and a legacy contexts list of plain strings beside it. On the probe payload the two lists agreed entry for entry. The reading below takes the checks list first because it is the form the API now returns, and falls back to the legacy list when the checks list is absent or empty.

The workflow probe used a workflow file as it stands in a workflows folder, with a name field, a triggers block, and two jobs. The YAML parser on this machine hands the triggers key back as the boolean True rather than as the string on, because the file spells the key in the unquoted form every workflow uses and the parser reads that spelling as a boolean under the YAML 1.1 rules. Any reader of workflow files must accept both key forms or it will find no triggers at all. A job with a name field displays under that name, and a job without one displays under its job id. Trigger entries for one event can carry branches and paths filters as lists of strings, and a job can carry an if condition as a string. A second probe with a matrix strategy confirmed the job record name form for a matrix job, which is the display name followed by a parenthesised combination in the same string.

The history probe used an export in the form of the jobs listing of the runs API. Each job record carries a name, a workflow_name, a status, a conclusion that can be null while the job stands unfinished, a started_at timestamp, and a completed_at timestamp in the ISO 8601 form with a Z suffix. The conclusions on the probe records were success, failure, and skipped, and the skipped form is a completed record whose conclusion is the word skipped, distinct in the data from a run that never happened because no record stands for it at all. That distinction in the records is what the skip obligations below are built on.

## Slice 2 obligations

S2-1. Protection ingestion. The protection input is a JSON object carrying a required_status_checks object. The required contexts are the context fields of its checks list in file order when that list is present and non empty, and the strings of its legacy contexts list in file order otherwise. A duplicated context collapses to its first position. A protection input with no required_status_checks object, or with neither list carrying an entry, is a reported error and never an empty pass. A context entry that is not a non empty string is a reported error.
Tests. tests/test_ingest.py test_protection_reads_the_checks_list_in_order, test_protection_falls_back_to_the_legacy_contexts, test_protection_collapses_a_duplicated_context, test_protection_without_required_checks_is_an_error, and test_protection_with_a_blank_context_is_an_error.

S2-2. Workflow ingestion. The workflows input is a folder, and every file in it with a yml or yaml suffix is read in filename order. The workflow name is its name field when that field is a non empty string and the filename stem otherwise. The triggers stand under the on key in either of the two key forms the parser hands back. The jobs stand under the jobs key as a mapping from job id to job spec, and a workflow file with no jobs mapping is a reported error naming the file. A job display name is the job name field when that field is a non empty string and the job id otherwise. A file that does not parse, or whose top level is not a mapping, is a reported error naming the file.
Tests. tests/test_ingest.py test_workflow_reads_name_jobs_and_display_names, test_workflow_name_falls_back_to_the_filename_stem, test_workflow_without_jobs_is_an_error_naming_the_file, and test_workflow_yaml_suffix_is_read.

S2-3. Trigger reach. A workflow can fire for the branch when its triggers include push or pull_request in a form that does not exclude the branch. The trigger forms are a single event string, a list of event strings, and a mapping from event to a config that can be empty. A branches list in an event config admits the branch only when one entry matches it under filename pattern matching, and a branches-ignore list excludes the branch when one entry matches it the same way. An event config with no branches filter admits every branch. A workflow whose triggers hold neither push nor pull_request, or hold both only in forms that exclude the branch, cannot fire for the branch and none of its jobs produce anything for that branch. A paths list or a paths-ignore list in a firing event config never stops the workflow from firing, and it is recorded as a note under S2-8 instead.
Tests. tests/test_reconcile.py test_schedule_only_workflow_produces_nothing, test_branches_filter_excludes_the_branch, test_branches_ignore_excludes_the_branch, and test_branch_pattern_admits_a_matching_branch.

S2-4. Producer matching. A job that stands in a workflow that can fire for the branch produces two candidate check names, its display name on its own and its workflow name and display name joined by a slash with spaces around it. A required context is produced by a job when the context equals a candidate, or when the context begins with a candidate followed by a space and an opening parenthesis, which is the matrix combination form. The producers of one check are every matching job across every firing workflow, ordered by workflow filename and then by job id.
Tests. tests/test_reconcile.py test_job_produces_by_display_name_and_by_workflow_form, test_matrix_context_is_produced_by_the_matrix_job, and test_two_workflows_can_produce_one_check.

S2-5. History ingestion. The history input is a JSON object carrying a jobs list in the form the probe states. Each record must carry a non empty string name, and its status and conclusion and timestamps are read as they stand, with a null conclusion and a null completed_at both standing for a job that has not finished. A record whose name is not a non empty string, or whose timestamps do not parse, is a reported error naming the record position. The history window is the span from the earliest timestamp any record carries to the latest, and an export with no records has no window.
Tests. tests/test_ingest.py test_history_reads_the_job_records, test_history_with_a_bad_timestamp_is_an_error_naming_the_position, and test_history_with_a_blank_name_is_an_error.

S2-6. Classification. Every required check gets exactly one status. A check with no producer under S2-4 reads no_producer. A check with a producer whose matched records include one that ran reads alive. A check with a producer whose matched records include none that ran and at least one that was skipped reads skipped_only. A check with a producer and no matched record that ran or was skipped reads never_run. A record ran when its status is completed and its conclusion stands in the set success, failure, cancelled, timed_out, and neutral. A record was skipped when its status is completed and its conclusion is the word skipped. A record in any other state counts as neither, so a check whose only matched records stand unfinished reads never_run. A record matches a check when its name equals a candidate of the check or begins with a candidate followed by a space and an opening parenthesis, and the candidate set of a check holds its producer candidates and its own context and, when the context carries the workflow form, the part of the context after the last slash joiner. The alive status is a report of fact and never a finding, and the other three statuses are the paper kinds this tool exists to name.
Tests. tests/test_reconcile.py test_alive_check_reports_its_last_run, test_renamed_job_reads_no_producer_with_a_stale_date, test_produced_check_with_no_records_reads_never_run, test_only_skipped_records_read_skipped_only, test_a_run_beside_a_skip_reads_alive, and test_an_unfinished_record_alone_reads_never_run.

S2-7. The last run date. The last run date of a check is the date in UTC of the latest finishing timestamp among its matched records that ran, where the finishing timestamp is the completed_at when it stands and the started_at otherwise, and timestamps carrying an offset are converted to UTC before the date is taken. A check with no matched record that ran has no last run date, and that absence is reported as an absence and never as a date. A skipped record never supplies a last run date, because a skip is not a run, and an unproduced check still reports the date of a run its context names in the history, because that stale date beside the missing producer is the evidence of the rename.
Tests. tests/test_reconcile.py test_last_run_date_is_the_latest_ran_record, test_last_run_date_converts_an_offset_timestamp_to_utc, and test_skipped_only_check_has_no_last_run_date.

S2-8. The two skips are different kinds. The skipped_only status is the success reporting variant, a job that stands in a firing workflow and is evaluated on the branch and whose skip satisfies the requirement while no step of it runs. When a producer job carries an if condition, the check report carries the note job carries an if condition, because the condition is the usual mechanism of that variant and the reader is told it stands there. A path filtered trigger works the other way, because a change whose paths the filter excludes creates no run at all, so a required check whose producer workflows are path filtered and which has no matched records reads never_run and never skipped_only, and its report carries the note path filtered trigger so the reader can tell a genuine absence from an ordinary one.
Tests. tests/test_reconcile.py test_skipped_job_with_an_if_condition_carries_the_note and test_path_filtered_producer_with_no_records_reads_never_run_with_the_note.

S2-9. The report. One report pairs every required check with its producers or its absence of one, its status, its last run date or its absence of one, and its notes. The JSON rendering carries the format string deadgate-report/1, the branch, the history window as a first date and a last date or as an absence, one entry per check in protection order, and a summary holding the required count and the alive count and the paper count. The markdown rendering carries the same facts as a table with one row per check in the same order. Both renderings are deterministic byte for byte on the same inputs, and the committed example under examples regenerates byte identical through the command line.
Tests. tests/test_report.py test_json_report_carries_the_whole_reconciliation, test_markdown_report_carries_the_same_facts, test_report_is_byte_identical_across_two_runs, and test_example_reports_regenerate_byte_identical.

S2-10. The command line. The command line entry point takes a protection file, a workflows folder, and a history file, with a branch option defaulting to main and a markdown flag selecting the markdown rendering over the JSON rendering. It prints the report to standard output and exits zero when the reconciliation completes, whatever the statuses are, because the statuses are the report and not a crash. A missing input file, or an input the ingestion obligations refuse, exits nonzero with a written error naming the input, and no traceback is shown for it. The tool reads local files only and makes no network call at any point.
Tests. tests/test_cli.py test_cli_prints_the_json_report, test_cli_prints_the_markdown_report, test_cli_missing_protection_file_is_a_named_error, and test_cli_refused_protection_is_a_named_error.
